# Concierge provider feasibility and open-source inspiration

Research date: **2026-09-12**. Planning evidence only; no integrations, bookings, scraping jobs, accounts, installations, or app changes were made. Public documentation and repository pages were inspected using web search/open. Search results sometimes included reviews; no review text, customer identities, listing prices, or live inventory was retained here. No authenticated provider API was exercised. Updated user fixture: Hawaii **November 30–December 14**, **four travelers**; year **2026 is an explicit planning assumption**, island undecided. Adult/child split, rooms, budget and Montréal dates remain unset.

## Decision for the implementation plan

Build a **complete handoff and return journey** first: a small shortlist of useful providers, a visible explanation of fit, the trip's search context, an external link, and a way to bring the chosen confirmation back into Voyalier. Add licensed data incrementally. Treat universal scraped inventory as an unavailable dependency, rather than silently replacing blocked providers with fabricated results.

The central implementation distinction is **documented interface**, **observed public destination URL**, and **unverified URL pattern**. A working destination page is not evidence that date, guest, room, amenity, price, or ranking query parameters are supported. “View stays in Montréal” is supportable with an observed public link; “See matching available stays for your dates” requires a verified search contract and current response.

There is no defensible universal “best travel website rated by people” in this evidence. Recommend providers by trip intent and actual capabilities. Let the user choose a default. Do not present affiliate compensation as evidence of quality.

### Flight-search entry points

Checked September 12, 2026: Google publishes route entry pages for [Chicago → Honolulu](https://www.google.com/travel/flights/flights-from-chicago-to-honolulu.html) and [Chicago → Montréal](https://www.google.com/travel/flights/flights-from-chicago-to-montreal.html), observed in its first-party search index. Use these only as route entry points, with dates, party, cabin, baggage and airports visibly confirmed on the provider. They are not verified parameterized searches for the four-person Hawaii trip. Honolulu applies only after choosing Oʻahu; do not silently use it for every Hawaiian island.

[Google's flight-search help](https://support.google.com/travel/answer/2475306?hl=en), opened directly, describes selecting dates/airports and usually completing the transaction on an airline or online travel agency website. [Expedia Flights](https://www.expedia.com/Flights), opened directly, is a second concrete entry point. These sources establish useful external workflows, not a public inventory-ingestion API or permission to scrape prices. No fare, schedule, date/guest URL encoding, reservation or cheapest-provider claim is retained in this plan. Preserve the copyable search brief and import-on-return flow.

## Proposed source and recommendation contract

This section is **design advice**, not a claim that provider agreements permit every proposed operation.

Each provider adapter should declare: supported intents and geography; documented vs observed link mechanism; evidence URL and check date; API/partner access requirement; allowed response fields; attribution/display requirements; cache and deletion policy; offline export permission; pricing/rating semantics; fallback URL; commercial/analysis rights; and disabled reason. Do not call an adapter usable merely because code compiles.

Each displayed recommendation should distinguish:

- **Why it fits:** deterministic user preferences such as whole home, kitchen, hotel service, proximity, car-free access, low exertion or food interest.
- **Evidence:** source name, source-native score and scale, review count when licensed, fetched time, canonical link, and unknown fields.
- **Status:** suggested / saved / booked from reviewed confirmation / cancelled. Keep these independent of ranking.
- **Action:** inspect the provider's results, compare candidates, save a candidate, or import confirmation.

Do not average Airbnb stars, Booking scores, Reddit votes and Yelp ratings into a single popularity score. Avoid provider-independent claims such as “best rated” unless the app defines the candidate set and comparison method and possesses the necessary current data and rights. A useful initial phrasing is **“Good places to start for your preferences”**, followed by two or three options and a clear reason each fits.

Treat provider-sponsored ordering and affiliate links separately from user fit. Keep provider-native content source-separated. Do not send API responses to an LLM for summarization or reuse until the relevant contract permits that operation; explicit user consent alone does not grant third-party content rights.

## Acquisition and scraping policy for the plan

The requested low-effort concierge can use automatic acquisition where it is authorized. Suggested priority:

1. Official structured APIs/feeds with approved access and recorded license.
2. Licensed partner APIs, with quotas, cache expiry, attribution, deletion and approved use enforced per provider.
3. Allowed official public-page extraction only after per-site terms/robots/access review, with a bounded parser, provenance, freshness and failure handling.
4. Public external links and the user's original notes/confirmations when ingestion rights or technical access are unavailable.

Do not implement a generic scrape-everything queue. Public readability, search indexing and `robots.txt` are not a license to copy reviews or build a competing inventory. Do not bypass login, CAPTCHAs, paywalls or bot blocks. A normal provider page opened by the user is a useful product action and should continue working when licensed data is unavailable.

For privacy, minimize handoff payloads to destination/date/party/filter fields. Passport scans/numbers, immigration status, account credentials, home address and document text must never be included in provider search URLs. Show what leaves the device when the user activates an external action; prohibit remote prefetch of personalized links before that action.

## Acceptance work for the implementation agent

- Fixture-test every URL adapter for Unicode destinations (Montréal), missing dates, invalid ranges, party/room differences, multi-island Hawaii, unavailable provider, and unknown location ID. No guessed identifiers or placeholder credentials in released links.
- Check every documented parameter in actual provider navigation using disposable trip inputs and the target browser. The current research did **not** verify Safari, installed webview, date persistence, checkout or authenticated behavior.
- For observed destination pages, verify destination and label. For documented API deep links, test the returned URL in sandbox where possible and clearly separate availability retrieval from external booking completion.
- Preserve a visible copyable search brief whenever automatic parameter transfer is unsupported. Opening a provider and coming back should keep all trip state and offer a next action.
- Simulate API access denied, timeout, quota exceeded, empty results, stale content and provider withdrawal. The cockpit must remain useful from local approved data, official links and a clear fallback.
- Test retention at provider expiry, deletion and offline export boundaries. A useful offline pack may contain original user notes and permitted sources while omitting expired/restricted provider data.
- Complete a provider-specific commercial rights and security review before activating partner API ingestion. Prices, dates and ratings in tests must be synthetic fixtures, not copied reviews or promises of a live deal.
